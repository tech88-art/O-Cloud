概览 · 拓扑

0 - 30 s /overview

绿色 健康 NPU · 红色脉动 degraded(预置在 a-02-npu-5)· 橙色虚线 PD prefill→decode pair · 蓝色虚线 inter-node fabric

操作清单

  1. 展示左中右三栏布局:资源树 / ReactFlow 拓扑 / 详情面板。
  2. 资源树自动展开:1 集群 → 3 节点 → 24 NPU · 退化 NPU 在 a-02-npu-5 已标黄色 warning。
  3. 点左侧树节点 → ReactFlow 同步高亮 + 详情面板翻转到节点卡(CPU / 内存 / NPU 数 / NUMA 布局)。
  4. 双击 NPU 节点 → 切片子树展开(默认折叠以保持画布清晰)。
  5. 顶栏切换 Include Fabric → 出现 switch + inter-node fabric-link 节点。
  6. 顶栏切换 Include Workloads → workload(灰⚙)+ pod 节点出现 · qwen-8b-pd 的 prefill-0 ↔ decode-0 之间出现橙色虚线 PD pair 标记(spec D6 · ADR-0005)。两 toggle 都开:125 节点 / 108 边。
  7. 右上 WebSocket 状态:● open · lastEventAt 随 events.json 滚动跳动(topology.update / npu.statusChanged …)。
讲解词:这是平台第一视图。我们从 1 个集群进入,看到 3 个节点 24 张 Ascend 910B NPU 的物理拓扑。 红色脉动的那张 NPU 是预置的故障样本,演示平台能识别异常硬件。 打开 Fabric 和 Workload 两个开关后,画布会一次性显示从硬件到业务的完整图谱 —— 这是 O-Cloud 跟传统 K8s dashboard 最不一样的地方,我们把异构硬件、网络拓扑、AI 推理业务融合到同一张图。

深度对比 · D6 NUMA+HCCS 亲和

150 - 220 s events.json @ t=180s

events.json 在 t=180s 后回放 D6 spec narrative · 同时启两个 Qwen-8B PD 工作负载, 同模型 · 同节点 · 同 NPU 代际 · 仅 NUMA 放置不同,看性能差异:

跨 NUMA 放置代价:TTFT +78% · ITL +79% · Throughput -40% · 同一台机器 · 同一型号 NPU · 只差 NUMA 放置策略。

讲解三段论

  1. 同模型、同节点、同 NPU 代际 — 唯一变量是 NUMA 放置。
  2. 跨 NUMA 时 TTFT 退化 ~60%、吞吐退化 ~40%,首 token 延迟和稳态吞吐都打折。
  3. 原因:HCCS group 共址 matters · prefill → decode 的 KV-cache 跨芯片传输用 HCCS ring · 跨 HCCS 强制走 UB-fabric 绕路。这是自研调度器插件的核心价值(NumaAffinity + HCCSTopology + Binpack 三件套)。
讲解词:到这里我们演示了"为什么这个平台不能只用 Ascend Device Plugin"。 传统插件只看"有几张卡",我们的调度器看"卡和卡之间怎么连"。 这组数字是 mock fixture 出的,但是差异比例是基于真实 vllm-ascend 行为校准过的(spec §D6)。
